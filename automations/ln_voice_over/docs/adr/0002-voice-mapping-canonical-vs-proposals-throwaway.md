# Voice mapping is canonical-accepted-only; voice proposals are a separate throwaway artifact

**Voice mapping** (`<series>/config/voice_mapping.json`) is the single source of truth synthesis reads to resolve a **Speaker** to a TTS voice. Every entry is **accepted** — there is no "proposed" status inside this file. **Voice proposals** (`<series>/config/voice_proposals.json` or chat output) are AI-generated candidate lists with rationales, fed into the **Voice-tuning project** for human audition; promoted entries are then copied (by the human, deliberately) into the voice mapping. Proposals are throwaway.

We chose this two-file split over a single file with a `status: "proposed" | "accepted"` field because the user pushed back on `status` as a concept inside the canonical artifact: synthesis should read a clean dict where every entry is real, not filter on status. Encoding the workflow in two artifacts (one canonical, one throwaway) instead of one mutable artifact also makes the human-in-the-loop step explicit — there is no path from "AI proposed" to "synthesis used it" that doesn't pass through deliberate human promotion. This mirrors the registry-gap workflow's "model proposes, human confirms, registry never auto-edits" rule established in ADR-0001.

A future reader looking at `voice_proposals.json` and wondering why it isn't read by synthesis should find the answer here: it is deliberately excluded so that synthesis output is reproducible only from artifacts the human has signed off on, and so that re-generating proposals (cheap, AI-driven) cannot silently change synthesis output (expensive, audio-affecting).
