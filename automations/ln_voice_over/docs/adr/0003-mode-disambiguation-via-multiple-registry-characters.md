# Character mode-disambiguation via multiple registry Characters

When a single in-fiction person has multiple voice-relevant **modes** (e.g. Kushida Kikyou's friendly public mask vs. her cold private self), each mode is represented as a **separate Character entry in the registry** with its own canonical name and its own **Voice mapping** entry. Attribution decides the mode at attribution time using bespoke per-character context rules; the canonical-data contract is preserved (every **Speaker** is exactly one registry name) and synthesis remains a pure dict lookup.

We chose this over two alternatives. One was **picking a single voice and losing the split** — cheapest, but the mask-on / mask-off distinction is exactly what makes Kushida a character worth voice-acting; collapsing it undercuts the point of speaker attribution. The other was **adding per-character variants to the schema** with a context predicate evaluated at synthesis time — flexible but speculative, since Kushida is currently the only character demonstrably needing this, and it would push complexity into synthesis that doesn't belong there. The "two registry entries" approach keeps the schema flat, the synthesis path simple, and the complexity localised to the attribution stage where it's already an LLM-driven decision.

The mode-disambiguation rule itself is bespoke per character — for Kushida, it's a "two of three signals fire" rule (audience composition, content tone, narrator framing) grounded in cross-volume source analysis (v4/v6/v7/v9/v10). A future character with a similar split copies the pattern (a second registry entry + a bespoke rule) rather than reaching for a generic framework. That generic framework is rejected today as speculation; it can be built later if 3+ characters end up needing the same shape — but most candidates probably won't, since most characters' words carry their tone without needing a different voice.

The implicit "these two canonical names refer to the same in-fiction person" relationship is currently undocumented in the registry. If cross-volume character bookkeeping ever needs it (e.g. counting a character's appearances across volumes), an explicit alias mechanism can be added then.
